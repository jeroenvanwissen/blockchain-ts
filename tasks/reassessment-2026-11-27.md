# Project reassessment 3: blockchain-ts

Date: 2026-11-27 (after Milestones 7 to 9, TASK-0037 to TASK-0055)
Scope: `main` at `e9ad941`. The whole node, with the attention on what changed since reassessment 2: the HD wallet and seed phrases, the explorer and API, Docker and multi-machine networking, and the storage rewrite (chain database, blocks on disk). The question was whether the node holds up against peers, operators and disks that don't behave, not only whether it works when everyone does.
Confidence: four reviews covered consensus, storage, P2P, and wallet/API/Docker. Every finding below was checked against the code. Findings marked *reproduced* were shown with scripts against real modules or real node processes in temp dirs (session scratch files, not committed; each task asks for a regression test). *Measured* means a benchmark on synthetic data; *inferred* is reasoning, not reproduced.

## Summary

The node works end to end and keeps working: CI passes every job on `e9ad941`, and a 20-minute soak with three node processes, payments and a SIGKILL converged with no warnings and flat memory. Much is sound:
- the consensus core (coinbase, fees, double spends, signatures, kernel, retarget);
- the wallet's cryptography (BIP32 and BIP39 match their reference vectors; scrypt plus AES-GCM);
- the API's authentication and the explorer's Content-Security-Policy;
- the ordering of block-file and database writes.

The gaps are adversarial:
- **Consensus:** a relayed block's signature isn't covered by its hash. Side blocks are stored and relayed with almost no checks. A rejection caused by the clock becomes a permanent invalid mark. Together these let anyone with a peer connection split nodes off the chain, fill their disks or force deep reorganizations. None of it needs stake or hashing power.
- **P2P:** a peer that stops reading makes the node buffer replies without limit. An honest node syncing a long chain gets banned by its own sync peer.
- **Wallet:** an unreadable `wallet.dat` is quietly replaced by a new wallet.
- **Design:** for a network that persists, there are no checkpoints and no limit on reorganization depth.

## Architecture and documentation

The architecture matches AGENTS.md:
- one validation path (`_connectBlock`), with the chain database as the chain state;
- blocks on disk, with the block index the only per-block structure in memory;
- writes in batches, and a StorageError that never marks a block invalid.

The findings are about inputs that architecture doesn't defend against yet: data that is relayed but not committed to by the block hash (F-036), side branches (F-037), peers that send slowly or not at all (F-038, F-043, F-044), and damaged or shared files (F-039, F-047, F-048).

Documentation that doesn't match the code:
- **AGENTS.md:**
  - "Rejections an honest peer can cause (races, clock skew, ...) must not score": descendants of a future-dated block do (F-041).
  - "Malformed or invalid peer data scores misbehavior": invalid transactions don't (F-052).
- **README:**
  - "Suspect chain state": `--reindex` doesn't rebuild a damaged database (F-048).
  - "The wallet routes never answer another machine" doesn't hold behind a same-host reverse proxy (F-055).
  - Status and the contents table still say every backlog task is done and link the first assessment as the latest (updated with this reassessment).

## Recommended sequence

1. **TASK-0056** (F-056): tests for every PoS block rule. Small, and the safety net for the next two.
2. **TASK-0057** (F-036, F-041): a block is marked invalid only for content its hash commits to, and never for the clock.
3. **TASK-0058** (F-037): side blocks pass header and proof checks before they are stored or relayed, with a bounded cost per block. Large; needs TASK-0057.
4. **TASK-0059** (F-038) and **TASK-0061** (F-043): send backpressure and a sync that doesn't trip the request limit. Both small, independent of the above.
5. **TASK-0060** (F-039): never replace an unreadable wallet. Small; can go first if wallet safety matters more than the network.
6. **TASK-0062** and **TASK-0063**: checkpoints or a reorganization limit, and the PoS time rules. Each needs an owner decision first (see open questions).
7. Then the P2 group, in any order:
   - TASK-0064: eclipse resistance
   - TASK-0065: API cost bounds
   - TASK-0066: data-dir lock
   - TASK-0067: storage recovery
   - TASK-0068: memory bounded by a cache
   - TASK-0069: wallet and API fixes
8. Then the P3 tasks: TASK-0070 (relay and peer-handling costs) and TASK-0071 (pending transactions across a reorganization).

## Open questions

- **F-040, checkpoints or a depth limit:**
  - Hard-coded checkpoints in each release are simple but need a release process.
  - A maximum reorganization depth needs no releases, but a node that was offline longer than that depth can't rejoin by itself.
  - The design this project follows uses checkpoints.
  - Either way it matters only once a network persists; until then a new genesis is acceptable.
- **F-042, future limit for PoS blocks:** keep 2 hours (as in the design this project follows), or limit PoS blocks to a few slots ahead? A tighter limit makes honest nodes with skewed clocks refuse more blocks. That is benign, but they fall behind until their clock is corrected. A second question: should an earlier slot win between equal-work siblings, before the tie-break value?
- **F-037, relaying side blocks:** should a node relay a side block at all before its branch has more work? Not relaying stops the spread, but slows how fast a competing branch reaches everyone.
- **F-054, fsync:** what durability should the block files and the wallet have? Fsyncing each block costs latency on every block. Fsyncing before each database commit costs once per batch.
